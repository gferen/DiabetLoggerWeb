# Action Plan — Structured данни за по-добър CGM анализ

Базирано на препоръките от логов анализ: разделен timestamp доза/хранене, физическа активност, алкохол, грамаж въглехидрати при хипо, дати на смяна ампула/сензор.

---

## Принцип

Всички нови полета са **опционални** (nullable) — не чупят съществуващи записи, съществуващия `type` enum остава съвместим. Backend схемата се разширява веднъж, после web и Android само consume-ват новите полета.

---

## Фаза 0 — Backend (Python/FastAPI + SQLite)

### Нови `type` стойности (разширяване на enum)

Текущ: `bg | fast | slow | ketones | meal`
Нов: `bg | fast | slow | ketones | meal | activity | alcohol | device_change`

### Нови nullable колони в `entries` таблицата

| Колона | Тип | Приложимо за `type` | Цел |
|---|---|---|---|
| `meal_time` | TEXT (ISO8601) | `fast` | Начало на хранене, отделно от `time` (момент на дозата) — адресира "най-голямата единична загуба на информация" |
| `carbs_g` | REAL | `fast`, `meal` | Грамаж въглехидрати — критично за корелация при хипо третиране |
| `activity_duration_min` | INTEGER | `activity` | Продължителност |
| `activity_intensity` | TEXT (`light`\|`moderate`\|`intense`) | `activity` | Груба интензивност |
| `alcohol_units` | REAL | `alcohol` | Количество (стандартни единици или мл), не свободен текст |
| `device_type` | TEXT (`ampule`\|`sensor`) | `device_change` | Кое устройство е сменено |

### Migration стъпки

1. SQLite `ALTER TABLE entries ADD COLUMN ...` за всяка нова колона (nullable, без default — backward compatible)
2. Обнови Pydantic `EntryIn` модела — нов `Literal` за `type`, нови опционални полета
3. Обнови `qa.py` test suite (236 теста) — добави тестове за новите типове/полета, провери че старите записи (без новите колони) все още се четат коректно
4. Обнови `/api/stats` ако искаме нов breakdown (напр. "хипо третирания с carbs_g vs без")

## Фаза 1 — Web frontend (`index.html`)

За всеки нов `type`, добавяме съответен tab/форма в съществуващата tab-bar структура:

| Tab | Нови полета във формата |
|---|---|
| **Бърз инсулин** (съществуващ) | + опционален "Начало на хранене" datetime picker (ако различно от момента на дозата) + "Въглехидрати (г)" |
| **Активност** (нов tab) | Продължителност (мин) + intensity dropdown |
| **Алкохол** (нов tab) | Количество (единици) |
| **Смяна устройство** (нов tab) | Радио бутон ампула/сензор |

Графиката/историята вече имат filter логика (`visibleEntries()`) — разширяваме да разпознава новите типове с подходящи икони/цветове.

## Фаза 2 — Android app (mirror на Фаза 1)

Точно същите полета, в стила на съществуващия `MaterialButtonToggleGroup` (BG/Бърз/Бавен) — разширяваме на повече опции, или втори ред табове. `addEntry()` функцията праща новите полета в POST body-то.

**Важно (научено от v0.8 debugging):** API конфигурацията е дублирана `MainActivity.kt`/`ChartActivity.kt` — ако добавим нов Activity за някой от новите типове, не забравяй `apiKey` попълване на новото място.

---

## Фаза 3 — Тестване/валидация

- Провери реален CGM запис с нов workflow (доза + отделно meal_time + carbs_g) — потвърди корелацията в анализа вече е измерима
- Провери device_change записите позволяват ясно разграничение "инсулин проблем" vs "сензор проблем" в бъдещ анализ
